RL fine-tuning experiment · prime-rl 1e53181 · verifiers wordle

Teaching Qwen3-1.7B to play Wordle

A 1.7-billion-parameter model starts out unable to finish a game. It gets a short supervised warmup on example games, then reinforcement learning against the real game engine. Its win rate is measured on 20 games whose secret words it never sees in training.

Result: 0% → 15% (full fine-tune) and 21% (LoRA) wins on prime-rl's example eval; 40.5% and 42.5% when the eval strips the model's reasoning the way training does.

Where it stands

    The task

    Each game is a seeded TextArena Wordle-v0 board, served by the verifiers wordle taskset. The model gets the rules once and then plays turn by turn. It may reason first, but its move is the first word it writes in square brackets, like [crane]. The engine answers with one mark per letter:

    G right letter, right spot Y in the word, wrong spot X not in the word
    • Six guesses. Secret words come from a list of 156 five-letter nouns.
    • A guess that repeats a word, isn't an English word, isn't 5 letters, or has no brackets is an invalid move. The first one gets a warning and a retry. The second ends the game.
    • The reward is the game's own score:
    reward = 1.0 if solved, else (greens + 0.5 × yellows) / 5 of the last valid guess
    Qwen3-1.7B28 layers, hidden size 2,048, 16 query / 8 KV heads, 151,936-token vocabulary, tied embeddings. A “thinking” model: it writes <think>…</think> before answering.
    T = 1.0Sampling temperature for every eval and for RL, as in prime-rl's Wordle example.
    1,024New tokens allowed per turn. Thinking counts against it.

    Why the base model loses

    Qwen3-1.7B thinks at length about every guess. In the baseline eval, 62% of its turns hit the 1,024-token limit before the thought ended. A cut-off thought has no closing </think>, so vLLM's Qwen3 reasoning parser returns the whole thought as the answer. The game then reads the first bracketed word in it, usually an earlier guess the model was quoting, and rejects it as a repeat.

    144 of 200 baseline games ended on a repeated APPLE that the model never chose to play twice. Its 0.17 average reward is mostly partial credit for that opening APPLE.

    SFT fixes the format: short thoughts and one bracketed guess per turn. RL then works on strategy: using the G/Y/X feedback, not repeating letters already ruled out, and finishing within six guesses.

    The same parsing affects the trained models in a quieter way: they often quote earlier guesses in brackets while thinking ("the feedback for [crane]…"), and the eval plays that quote. Training never sees this, because prime-rl's renderer strips the thinking before the game reads the move. See Results.

    Because of this, the format-error rate here counts every turn that failed to produce a well-formed move: cut off at the limit, or rejected for having no [word] or the wrong length.

    Keeping the test honest

    The win rate means something only if the eval words are new to the model. At the pinned versions, the stock example setup leaks them three ways:

    1. The example's eval plays seeds 0–19, and training also starts at seed 0. The eval games get trained on within the first three RL steps.
    2. There are only 156 secret words. A run of a few thousand games sees every word many times, so different seeds alone hold nothing out.
    3. The SFT dataset, willcb/V3-wordle, has 98 of its 1,000 games ending on one of the eval words. It covers all 18 of them.

    So the 18 distinct words behind seeds 0–19 are held out everywhere. Training uses seeds 20–6019 minus the 675 whose word is an eval word, which leaves 5,325 games over the other 138 words. Loading the taskset with the exact training selection confirms that no eval seed and no eval word appears. The SFT data drops its 98 affected games, leaving 902.

    18 eval words (held out) 138 training words

    Held-out words make these numbers harder to compare with prime-rl's published ~60% win rate, which was measured without this split.

    One RL step

    1. The orchestrator picks 8 training words and asks for 16 games on each: 128 games.
    2. vLLM plays them against the env server, which runs the real TextArena engine in 16 worker processes.
    3. Each game's advantage is its reward minus the mean reward of the 16 games on the same word (prime-rl's default grpo, without standard-deviation scaling). Every token the model wrote in that game carries that advantage.
    4. The trainer takes one AdamW step with the IPO loss: an importance-weighted policy gradient that drops tokens whose probability moved by more than 0.3 since sampling.
    5. New weights go to vLLM over NCCL. Generation keeps running while the trainer updates, so some games are sampled by a slightly older policy; the importance weights correct for it. In this run the oldest were up to 8 versions behind.

    The LoRA run is identical except that only rank-32 adapters on every linear layer train. The 1.7B base stays frozen. Its rank, alpha and learning rate are the settings from prime-rl's LoRA example (alphabet-sort). Adapters reach vLLM as files and are swapped in live.

    Architecture

    The env server runs each game and calls vLLM for every model turn; the orchestrator batches finished games, computes group advantages and feeds the trainer. Drawn with archify.

    • Mac. Holds the code, configs and results. It ran a 5-game local test against a 4-bit MLX copy of the model, rents and destroys vast.ai instances through scripts, and runs a watchdog that pulls results and destroys the instance after 15 idle minutes.
    • Instance. Image nvidia/cuda:13.0.1-cudnn-devel-ubuntu24.04. Setup installs uv, clones prime-rl at the pinned commit and syncs about 16 GB of wheels, in about 6 minutes. Every long job runs in tmux and logs to a file.
    • What comes back. Eval traces, training metrics, logs and the LoRA adapter. Full-model weights and RL rollout traces (~4.6 GB per run) stay on the instance.

    What broke, what fixed it

    CUDA 13, not 12

    At the pinned commit prime-rl ships torch 2.13 built for CUDA 13, cu130 flash-attn and nixl-cu13. Fix: the image prime-rl's own Dockerfile uses, on hosts whose driver supports CUDA ≥ 13.0.

    RL needs two GPUs

    rl runs vLLM and the trainer on separate GPUs, with no shared-GPU mode. Fix: the smoke test used 2× RTX 3090 instead of one.

    GitHub 504s stopped every run

    uv run re-resolves the project on each call and re-downloaded the flash-attn wheel from GitHub, which was returning 504. Fix: UV_NO_SYNC=1 for every run; setup does the only sync.

    Triton couldn't compile

    The bare CUDA image lacks Python.h, and Triton compiles a small C helper at startup. Fix: install python3.12-dev during setup.

    Eval words leaked into training

    Shared seeds, a 156-word pool and SFT games on eval words. Fix: a held-out split by secret word, applied to both RL seeds and SFT data, and verified against the loaded taskset.

    Cut-off thoughts became moves

    A thought truncated at 1,024 tokens was handed to the game as the answer. Fix: the format-error metric counts those turns per turn, so the baseline's 62% shows up instead of hiding as “repeated guesses”.

    RL was 3× slower than it should be

    Building one Wordle game takes 0.87 s of CPU. The default elastic env pool kept every game in one worker until about 115 were in flight, so each new game stalled the rest, and vLLM sat at 4 running requests. Fix: a static pool of 16 workers. A step went from 3.5 min to about 70 s, with the same rollouts.

    The eval read moves out of the thinking

    The example eval server has no reasoning parser, so the game took bracketed words from inside <think>. Training reward ended near 0.7 while eval reward sat near 0.45. Fix: the official numbers keep the exact example eval, as planned. A second run of the same eval adds --vllm.reasoning-parser qwen3 to the server and shows what the models actually learned: 40.5% and 42.5% wins.

    Disk on both ends

    A full fine-tune checkpoint is 21 GB, and two exist briefly at each save. Fix: delete the SFT optimizer state after export. RL rollout traces (~23 MB per step) stay on the instance, because the Mac has only a few GB free.
